**193 条中有 110 条附带可运行的 `repro.sh`。** 其余条目是通过阅读固定版本的源码并手工运行工具确认的；每一条都注明了它是针对什么验证的、工具实际输出了什么，且大多数都点名了你本地仓库中已经存在的测试样本（fixture）。对于"不可达代码"之类的断言，靠阅读代码本身就能定论——再打包一个用于演示"静默"的脚本毫无意义。

每个工具目录都有自己的索引、自己连续的编号，以及一份 `run-all.sh`。这里面的内容互不依赖。

## 严重度（Severity）

只有一列，它衡量的是**对当今所签发证书的影响**：即该缺陷是否会让针对当前签发证书的判定结果发生改变。它刻意**不是**对缺陷"有多 alarming（吓人）"的度量，也**不是**出现频率。

一个可以被关闭的检查，无论是否真的有人关掉它，都是严重的问题——因此"覆盖面（reach）"不被计入严重度。**本包中任何地方都不出现 corpus（语料库）计数**：用一个你并不掌握的 corpus 量出来的数字，是你无法核验的，而且会诱使人把频率误读为严重度。

## 用例（Cases）

每个条目都有 `positive/`——即能够证明该缺陷的证书。当缺陷表现为一种*差异*时，`negative/` 存放对照组：即在同一字段上有所不同、但工具能正确处理的同一张证书。一对用例才能证明机制；单单一份文件只能展示输出。

`positive/NONE.md` 表示该复现是临时构造的输入，或者该条目讨论的是工具永远执行不到的源码。

## 本包不是什么

它不含我们自己的任何 Linter，不含指向我们内部代码树的任何路径，也不引用我们自己的任何编号。每一条断言都可以用这里的工具和文件核验。

所有条目都 `Confirmed`（已确认）：每一条都在被编号之前，针对固定版本做过复现，这也是为什么编号没有空洞。我们调查过并证伪的断言不在此列——而且这类数量多得令人不安：大约七分之一的断言没能经受住与工具的"正面接触"。

关于**四个工具全都没有覆盖**的合规要求，参见 [MISSING-LINTS.md](MISSING-LINTS.md)。
